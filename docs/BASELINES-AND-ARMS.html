JevLoop · 基准与对照

我们和谁比、为什么这么摆

论文要主张的是「判定放在哪、由谁读什么来做」。这件事决定了对照该怎么挑： 对照必须变的是验证者，而不是 agent 的推理方式。下面是我们现在手里的对照、 按 claim 的轴重排的结果、新补的三格、明确不做的两格，以及一次实测。

一先说一个要撤掉的东西

experiments/baseline/ 里本来有六个臂：direct、act、 react、reflexion、plan_then_execute、rewoo。

它们是上一版 idea 的 baseline

那六个变的是「agent 怎么推理和行动」——ReAct 加不加 Thought、Reflexion 失不失败后反思、 ReWOO 分不分规划与观测。而我们现在主张的变量是「谁在生成之后做那次判定、它有没有和证据耦合」。

拿它们当主对照，等于在回答另一个问题。所以不是"能不能用"，是"用在哪儿"—— 详见第四节的重排。

而且仓库自己早有一条判据，正好能拿来筛：

baseline/README.md 里已经写着

Reflexion(uses_success_signal=True) → 吃金标（用环境给的成败信号）
Reflexion(uses_success_signal=False) → reflexion-selfeval，LLM 自评，不碰金标

⇒ 吃了金标的臂不能和没吃的同列一张表（部署时拿不到金标）。这条直接成了筛选标准之一。

二挑选标准（四条，缺一条就不该进主张那张表）

  1. 它必须变"验证者"，不是变 loop 形状。否则比出来的东西跟 claim 无关。
  2. 它不能碰金标。部署时拿不到；碰了的只能单列。
  3. 它要落在 claim 的某一根轴上（谁判 / 判几次 / 什么形式）。落不到轴上的，最多当"能力没退化"的附行。
  4. 两种都要有：业界常规做法（证明对照组不是稻草人）+ 有出处的文献方法（证明我们不是闭门造车）。

四本期新补的两格 + 抬起来的一格

① react-termination —— 终点验证（原计划叫"关键比较"）

和 react-typed 只差一件事，而且是构造保证的：两者共用同一个 run_loop、同一个 build_prompt、同一批工具、同一个交付闸门 （TypedController._can_deliver 逐字复用，没有第二份实现）。差别只在"判定放几次"：

臂循环中间终点
react-typed每一步都问（六个节点）问 canDeliver
react-termination一次都不问问 canDeliver
一个必须先说清的语义

这道闸门不是拦截器。全契约的原话是「上限 1 次：第二次还不合格就如实交出去并说明」。 两条臂照抄同一套（连上限都一样）——否则比的就变成"会不会拒答"，而不是"判定放在哪"。

② react-selfcheck —— 零资源自检（SelfCheckGPT 那个思路）

核心想法一句话：同一段提示多采几次；模型真知道的事会前后一致，编的事会发散。 它不需要外部知识库、不需要金标、不需要另训模型。我们的移植是：在终点用同一份 (任务 + 已发生的工具历史) 再采 k 次，算与原答案的平均一致度。

三条偏离，必须跟数字一起报：

  • 它的判据是"自洽"不是"正确"。一个稳定地犯同一个错的模型会拿高分——这是该方法公开的已知弱点，我们用一条测试把它钉成了预期行为，免得将来被当 bug"修"掉。
  • 它要花 k 次额外生成。省掉的是判定后端的钱，不是模型的钱。
  • 它看不见工具输出的真假。它比的是"我再说一遍还这么说吗"。⇒ 在工具撒谎那一类条件上它结构上抓不到。这条是可证伪的预言，也是这一格存在的理由之一。

③ reflexion-selfeval —— 从范式消融里抬出来当验证者

它本来只是 Reflexion 的一个开关，但它的语义恰好是"找一个 LLM 自评、不碰金标"—— 那正是"业界常规验证者"的那一格。现在它在臂目录里被显式当成一条对照，而不是一个脚注。

五明确不做的一格：PRM / ORM

不做，而且是写进论文的"不做理由"

过程/结果奖励模型是训练出来的验证器（要在带步级标注的数据上训一个模型）。 它们变的是"验证者怎么来"，和我们的自变量（放在哪、读什么）不是同一根轴； 而且一训就引入训练数据、算力、超参三个新变量，会把"位置"这个变量淹掉。

不是做不到，是它换的是另一根轴。

六一次实测：三个终点验证者，同一个循环

ternary-judge（有工具的检索任务）20 题 · 生成 qwen3.5-9b · 判定模型 Jev

臂答对闸门假拒闸门放过生成调用判定请求
react（没有验证者）15/2000690
react-termination（终点·判定模型）15/20056920
react-selfcheck（终点·零资源自检）15/20411370
react-typed（全程七节点）3/2001149273

四条读法，前三条比数字本身重要：

  1. 三条"终点"臂的成绩都是 15/20，只有全程那条掉到 3/20。 ⇒「判定放得越多越好」在这个数据集上不成立。这一格说的是位置，不是"终点验证更好"。
  2. react 那行的 0/0 是"构造上没有闸门"，不是"闸门从不犯错"。 并列时必须写清 —— 否则读者会以为"没有验证者最准"。
  3. 零资源自检的代价形状是真的：判定请求 0 次，但生成调用翻倍（137 vs 69）。 ⇒「自检更便宜」只对判定后端成立，对生成不成立。
  4. 终点这一步上两者的错法相反（n=20，只能当方向）：判定模型没有误拒任何正确回答， 但 5 条错的都放过了；零资源自检拒掉了 5 条错里的 4 条，代价是误拒了 4 条对的。 这正是"自洽 ≠ 正确"的实测形状。

七顺手修活的两个死指标

它们以前恒为 False

results.jsonl 里一直有 gate_false_reject / gate_false_deny 两栏， 而它们恒为 False：记账代码从 failure_class 里读 "gate_rejected_correct" / "gate_passed_wrong"， 而整棵树里没有任何一处产生过这两个值。

信息其实一直在控制器手里，只是从来没往回传。现在按 (闸门第一次裁决 × 判分结果) 算：

闸门假拒第一判说 revise ∧ 最终答案是对的 ← 它拦了一个好答案
闸门放过第一判说 deliver ∧ 最终答案是错的 ← 它放了一个坏答案

取第一次裁决，不是最后一次：修订之后再判的那个数已经被闸门影响过了， 拿它算"闸门错没错"是循环论证。

另外修掉一个坑：跑臂的入口原来是 needs_decider = agent.endswith("-typed") —— 靠臂名的后缀去猜它要不要判定后端。新臂不以 -typed 结尾，于是判定后端没建、 连候选目录都进不去，报出来却是「没有这个 agent」，而那句报错里的目录读的是两个空注册表， 看起来像整个项目什么都没接。能力是属性，不是拼写——判据已改，报错也改成列真实目录。

八还缺什么

  • 把一个数据集上的这张四臂表，在第二个数据集上重复一遍。 现在第 4 条那条"错法相反"只有 20 题、一个模型，分不清是方向还是噪声。
  • 异族判官（judge-other）的数据不全 —— Llama 那条只在 1 轮里跑过。
  • 坏条件上的自检预言还没验：预期它在"工具撒谎"那类条件上抓不到东西 （它看不见工具输出的真假）。这是个可证伪的预测，应该去跑。
  • （CoVe、PRM 的具体实现我没有核过；上面 SelfCheckGPT 的仓库与 CRITIC 的全文页是核过的。 补臂之前按仓库既定的有界检索方法再过一遍，每个来源标核验级别。）
