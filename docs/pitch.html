以前是啥样的

判定不是不存在，它寄生在别的东西里

懂行的人会说：LangGraph 里就有 should_continue，位置明明是显式的。对 —— 所以差别不在有没有，在它是什么形态。三种常见形态，后两种最普遍。

① 融进生成 看不见它看了什么

用模型输出的一个标记来表示判定结果。判定与生成共用一次前向，也共用「上下文里有什么」—— 输入无界、不可声明。

② 融进计算 不读语义

撞上限就停、字符串里有没有 DONE。这是用计算冒充判定：它读的不是语义，是形状。

③ 有位置、没规格 最常见

节点是显式的（should_continue），但它的规格是零：允许看什么、答案集合、每个答案对控制流做什么、留没留记录 —— 全没有。

// 形态①：判定融进生成 —— 「做完了」是模型生成出来的一个标记
const res = await llm(`${systemPrompt}

Conversation so far:
${JSON.stringify(messages)}

If the task is complete, reply DONE.`)
if (res.includes('DONE')) break   // 形态②：判定融进计算
  • 它看到的是 messages —— 「给判定看什么」不是一个可以声明、可以检查的东西，它是「上下文里恰好有什么」。
  • 判据是一句英文散文。没有任何机制能告诉你：它被喂了判这件事所需的证据没有。
  • DONE 到「结束整轮」的映射是隐式的 —— 换个人接手，第一个人猜错。
  • 离门限多远、谁答的、能不能换后端答 —— 一个都问不出来。
我们观察到了什么

四个缺陷，都是真实事故，不是假想

下面每一条都来自这个仓库的原型阶段，且都记在文档里（含坟头）。共同点：没有一个会报错。

① 计数冒充判断 静默

帧里放的是 steps_done: 2。任务「把 alpha.ts 里的 totalOf 抄到 summary.ts」，读完 alpha.ts 之后判了「不需要工具」 —— 文件从没被写出来。
因为「读过」和「写过」在一个计数里长得一模一样。

② 候选项没有区分度 静默

曾有一个「写哪个文件」的判定，候选＝已存在的文件，判据＝「任务要求改它」。每个选项都在声称同一件事 —— 模型给选中项 1.00 的把握，然后选错。
那不是判定，是让模型在无差别选项里掷骰子。

③ 拿不到内容就填占位符 有副作用

取不到写入内容时，代码填了一个占位符字符串 —— 而它真的被写进了目标文件。
「容错」在这里变成了往用户盘上写垃圾。

④ 不可信文本挤掉判据 19.5%

给不可信通道加标记的实测开销：7 个标记、784 字符 / ~4 KB 帧 = 19.5%。「给判定看什么」是个真取舍，不是格式问题 —— 而传统形态下它根本没被当成一个问题。

四个缺陷共享一个形状：循环得出一个证据不支持的结论，而全程没有任何地方说过一句不。
提出来的概念 · 一

三分法：循环里每一步只做三件事之一

判据谁来答贵不贵
计算一个不读自然语言的函数就能判出来代码免费、可单测
判定答案在闭集里，但要从非结构化内容里读出来判定模型 / 规则表 / 桩一次判定请求（或编译掉）
生成答案枚举不出来（自由文本、任意路径、任意内容）生成模型最贵，且无界

界线一：计算 / 判定

if (!existsSync(p)) 是计算 —— 不读自然语言。
「这一步成没成」是判定 —— 要看工具输出。

界线二：判定 / 生成

能不能枚举答案。
「选哪个工具」「要不要授权」「做完了没」能枚举 ⇒ 判定。
「写什么内容」「移到哪个新路径」不能 —— 目标不在任何闭集里 ⇒ 生成。

这条线不是审美：它决定花不花钱（候选项已知的判定可以编译成策略，不发给模型）， 也决定归谁管（判定是数据，可换后端；生成是自由文本，塞进帧里只会挤掉别的）。
提出来的概念 · 二

判定层 = 答案在闭集里、要从自然语言里读出来、并且会改变控制流的分支点

为什么「拆出来」在技术上有抓手

抓手就是闭集这一个性质：判定的答案在有限集合里，所以它不必由生成模型回答。这条推论一路走下去就是全部价值：

  • 候选已知、判据可写成条件句 ⇒ 编译成策略，零模型调用；
  • 要模型答 ⇒ 换后端不动循环 ⇒ 可注入（规则表、分类器、测试桩）；
  • 答案在闭集里 ⇒ 动作可以穷尽检查（14 个动作的语义是驱动真循环对账出来的）；
  • 有帧 ⇒ 「它该看什么」可以机器核对。
判定有闭集答案，所以它可以不是生成的一部分。拿出来之后，它可以被编译、被替换、被检查、被记录。

两种界：判定侧 / 执行侧

界的是什么落点
判定侧它能看什么帧预算 + 显式排除
执行侧它能做什么输入/输出上限、超时、隔离

grade_risk 正好坐在交界上：它是判定，但它判的是「接下来那次执行有多危险」。这也解释了为什么「能写多少」不写在判定里，而是执行侧在 run() 之前检查 —— 判定只负责授权。

一个用词约定

判定＝一个闭集问题的回答（is_done → finish / keep_going）。
决策（decision）＝整条记录：帧 + 答案 + 策略 → 动作 + 指纹。
所以「决策层」听起来比实际的大；实际是判定层，加一份可复核的记录。

具体怎么实现 · ①

一个判定就是一个块：问题 + 闭集选项 + 有界帧 + 策略

根目录一份 DECISION.md，编译成 7 个节点。这是交付闸门（该不该把这份回答发出去）：

## can_deliver
kind: mixed
when: after-generate —— 生成之后，回答发出去之前

### unsupported
ask: The answer states something that the tool output does not support
- true — it claims a fact, file or result that was never observed

frame:
  + task       400                —— 判据是「任务要求的事做了、并如实报告」，两边都要有任务
  + answer     900  draftMaybe    —— 判的对象就是刚生成的这份草稿
  + evidence   600  writeEvidence —— ★ 交付闸门要拿工具结果逐句核对回答，所以预算比别处宽
  - cwd                           —— 与「回答有没有证据支撑」无关
  - readFiles                     —— 读过哪些文件同样不是证据本身
  - lastResult                    —— 最近一条结果已逐字在 evidence 里，单列会让最近一步获得不成比例权重

policy:
  - prob:unsupported >= 0.5 → revise
  - prob:deliverable >= 0.6 → deliver

帧是有界的

每一格有字符预算；不看的格要点名，并写出为什么。

选项是闭集

14 个动作，每个声明 next / endsLoop / moreModelCalls / needsEvidence / retries。

策略是可编译的

门限 + 谓词 → 纯函数。候选项已知时，这道判定不发给模型。

具体怎么实现 · ②

四层检查：写错就在加载期失败，而不是编译成一条永不触发的规则

层查什么
parse语法、kind、闭集的动作与位置、每一格必须有界
policy每个谓词必须能编译 —— 编译不了的闸门永远不会触发
frame每一格状态要么被某道判定读了、要么被排除并写了理由。没有第三种状态
schema版本缺失或不认识 ⇒ 拒绝，不是猜着读
conformance：15 / 15 个「会安静地判错」的改法被拦下；
4 / 4 个「意思没变」的改法没被误伤（阴性对照）。

一个能立刻看懂的例子

把 can_deliver 帧里那一行排除项删掉：

- cwd    —— 与「回答有没有证据支撑」无关   ← 删掉它

npm run conformance 失败，并点名 cwd。

在它存在之前：四层全绿，cwd 就这么从声明里消失了 —— 判定的输入悄悄变大，没有任何人知道。

投影表是封闭的

编一个不存在的投影名，解析器当场抛：投影 'cwdLength' 不在注册表里。
这是真的加载期拒绝 —— 而「漂移期的拒绝」住在适配器里，见第 10 页。

具体怎么实现 · ③

每条判定留一份可复核的记录，而且人读的那一份就是可审计的那一份

记录里有什么

node, state            ← 当时真正发出去的那份有界帧
frameDigest          ← 该节点自己那份帧
sentFrameDigest      ← 实际发出去那份（合并判定时不同）
batchIds, sentQuestions ← 哪几个节点合并成一次前向
requestDigest        ← 帧 + 实际发出去的问题集
questions, answers, action, reason, provider

npm run replay 给四档结论：verified / partial / unverifiable / mismatch。

一个决策一个 .md（decisions/2026-09-29-001.md）

  • 可读：结论、节点、动作、理由、当时发出去的那份帧、问答、指纹。
  • 可复核：记录原样嵌在文件里，--verify 只读 .md 就能重算指纹。
  • 正文也被核对：从机器可读块重算正文并逐字比对。改渲染出来的表格？报出来。

为什么非要做最后那一条

第一版只查那个块。于是把表格里的命令从 ls -la 改成 rm -rf /，照样报 verified —— 因为改的不是那个块，而人读的恰恰是表格。一份能被人读出错误结论却报 verified 的文件，不算可审计。

具体怎么实现 · ④

两个消费者 —— 以及一个真实宿主告诉我们的事

① 参考循环 src/

内进程。判定是数据，所以整套 bench 与实验都能拿规则表或桩驱动 —— 没有这条，我量不了任何东西。

② 一个我们不拥有的宿主 adapters/codex/

Codex 的 hook 面，真在 codex exec 里跑起来过：ls -la 被契约判为 ask_human 并拦下，记录重放 verified。

而在真实宿主上，六个位置只有三个够得着

位置够不够得着为什么
before-call完整PreToolUse + PermissionRequest
input-choice完整同上
after-tool部分PostToolUse / Stop
tool-choice结构上不可达PreToolUse 在模型已经选完工具之后才触发
step-start不存在每个模型步之前没有任何 hook
after-generate不存在生成完没有拦截点
哪些判定能被适配，由宿主的扩展面决定，不由哪些判定重要决定。
参考循环里最常被引用的 pick_tool，在那里恰恰接不到。而 ask_human 根本表达不了（它的 parser 拒 ask）⇒ 映射成 deny，fail closed。
我们量了什么 · 含对自己不利的

falsification 条件成立：契约门没有可测优势

先把能证明的说清楚：can_deliver 的策略就是一条 if/else 链，所以策略层不可能有优势。差异只能来自「帧怎么编、怎么校验」。于是只变那两处，门限逐字抄成一样。

臂一致假接受假拒绝拒绝
contract （照参考实现真实行为）33090
contract-strict （+ 适配器纪律）30066
ifelse-best （带守卫的手写门）30066
ifelse-naive33090

逐格比较：contract ≡ ifelse-naive，contract-strict ≡ ifelse-best，在所有扰动上完全相同。

更正一：拒绝是适配器的

参考实现把缺失的格记进 unfilled，然后没人读它（grep 过：src/ 里唯一命中在注释里）。所以「照契约跑」和一个从没想过漂移的手写门不可区分。

更正二：0 假接受不是安全

证据一空，每条主张都不被支持 ⇒ 闸门把每份回答都打回。它不是判得更准，是停摆了。这就是为什么每张表都报两根轴。

更正三：抓不住自洽的错帧

真跑那次，适配器拿错的 task（codex 塞的环境块占了「第一条用户消息」）判了 4 条，replay 报 4 verified / 0 mismatch。
帧有界、指纹全对、可重放，而判定建立在错的东西上。

唯一没被证伪的声明是「漂移检查可导出」—— 加一格声明/改一个界，检查自动跟上，零行检查代码改动。
但它很薄：按依赖集量，勤快的手写门也是 100%。差距只在依赖集变化时出现：0 处改动 vs 1 行守卫。
⇒ 留下的是一致性性质，不是能力性质。
边界与邀请

我们不主张什么 —— 以及我缺的那一块

明确不主张

  • 不主张判得更准 —— 上面那个实验说的是没有差异。
  • 不主张快 —— 一次判定只要 78 ms 计算（一次生成是 2000+ ms），但托管 API 上它还要付 254 ms 握手，合计 ~390 ms/判定；13 次判定 : 1 次生成时判定主导墙钟（79%）。在那种延迟下，「判定很便宜」是假的。
  • 13 : 1 是判定次数 : 生成次数，不是「省了 13 次模型调用」。一个像样的 ReAct 循环大概只要 3–4 次调用。
  • replay 不说明判定对错，也抓不住自洽的错帧。
  • 没有第二个实现者。跨宿主结论目前只覆盖一个宿主，而那还是我们自己写的适配器。

价值落在哪（诚实的尺寸）

买到的是可检查、可替换、可审计，不是更准。
而跨宿主一致性与第三方可审计性—— 契约真正多出来的那两样 —— 要等第二个消费者才兑现。

我缺的那一块

不是 review，是你把 DECISION.md 接到你的 loop 上，然后把卡住的地方告诉我。按预期，最先咬人的顺序是：动作语义（这边 14 个动作、你那边可能只有 4 种裁决）、动态候选提供者读哪几格、判定用哪个模型答。
