JevLoop · 研究计划

控制不是生成

我们研究的不是"怎么让模型判得更准"，而是： agent loop 的控制流，能不能成为一个可以被独立测量、并且以证据（而不是文本）为输入的对象。 这条 claim 底下有三条推论、一条界，和四个还没补上的缺口。

控制不是生成——
生成的产物，不能同时充当它自己的验收标准。

这是一条区分，不是一条处方。处方（"退出应该是一个判决点"）会招来"凭什么"； 区分不会——它指出的是两件被当成一件事的东西，其实不是一件。一旦接受，你就没法再把它合起来看。

更关键的是，它把"要分开的东西"从执行者挪到了判据。 这正是它比"把判定从生成里解耦出来"高一档的地方，也是我们那条最难看的数据能被解释的原因： judge-same 在执行者上已经完全解耦——换模型、独立进程、专门接口—— 却只动了 0/72、0/72、1/120 格。若 claim 是"解耦"，这是打脸； 若 claim 是"控制不是生成"，这正是它预测的失败方式：分开的是答话的人，没分开的是判据。 一个 claim 能把自己最难看的数据解释成支持，通常说明它是真的。

要防住的一种误读

"控制不是生成"不能被读成"模型不可信，所以要用规则"。它讲的是判据的来源， 不是执行者是谁。我们自己的数据把这两种读法分开了：规则是确定性的地板， 而耦合证据的判定器比不耦合的强 3.6 倍（见第三节）。 这句话不写，reviewer 会把这篇当成一篇 guardrails 论文。

如果控制不是生成，那么……我们手上已经有的东西
控制必须被声明七个节点；DECISION.md
控制必须被单独测量两个数（抓取率 / 假警报率）、配对操作、换证据
控制可以被单独路由和开关谁判 / 判几次两条轴；影子模式
控制的正确性有自己的界证据的可信度是上界（34%，18/53）
"完成率"必须和任务成绩分开报41–44% 误导性交付的那个量级

一问题：loop 的控制是生成的副产品

今天所有 harness 都是同一个形状——控制流没有人声明、没有人测量： 

while 模型还在发工具调用:
    a = LLM(历史)
    if a 是工具调用: 执行，结果塞回历史
    else: 结束          // 控制权在生成模型手里

这条退出条件是整条 loop 里最吃重、却最少被审视的一行。而它恰好是我们测到最容易出事的地方： 不加闸门、生成什么就交什么的时候，误导性的交付占 44.2%（53/120）； 换成全新生成的候选，是 41.3%（99/240）。 前一个数来自特意为造出这个类而写的任务集，所以那是密度、不是真实世界的发生率—— 但两组指向同一件事：假完成就是"最像样的下一段续写"，判据和错误同源。

更麻烦的是评测看不见这件事。大家报的是任务成功率，那个数把"写得对不对"和"控制得对不对" 混在一起，所以它永远回答不了"这条 loop 本身是不是健全"。我们最早的对照实验跑了 81 个格子， 只观察到 1 个事件——在那个密度下，"两组的平均差"在数学上就估不出来。

所以我们换两件事：把控制从生成里拆出来，并且给控制本身找一把尺子。

2.2 伪代码

传统：退出是生成的一个形状

while True:
    a = LLM(历史)      # 动作 + 停不停
    if a 有工具调用:
        历史 += 执行(a) # 无条件进上下文
    else:
        return a       # ← 退出

改写后：退出是一个判决点

while not 已交付:
    if 需要工具吗():   # 判决点
        t = 挑工具()   # 判决点
        历史 += 准入判决(执行(t))
                       # 判决点
    else:
        d = 生成交付草稿()
        v = canDeliver(d, 状态, 证据, 任务要求)
                       # ← 判决点：退出
        if v == deliver: return d
        if v == revise:  按缺的证据修一次，再判
        else:            如实报告，不假装完成

2.3 差在哪

差在哪传统 loop退出是判决点
谁拥有结束的权力 生成本身——它停止发工具调用，循环就结束了 判决——生成只能提议完成，关闭要由一次裁决来做
退出判据从哪里来 生成物的形状（没有工具调用了） 一份声明过的字段集：声明、状态、证据、任务要求
观测怎么进上下文 无条件塞回历史——上下文是日志 先过一次准入判决——上下文是判决记录
能不能被测量 不能：没有裁决值，也就没有分子分母 能：抓取率、假警报率、弃权率，逐点算
能不能被路由 / 开关 不能：没有可替换的接口 能：每个点可以单独换判定器、单独关掉、单独跑影子模式

后两行是重点。前三行说的是"更合理"，第四、五行说的是"从此可以被检验"。 一篇论文能站住的通常是后两行。

2.4 它戳的是评测

这一条推论真正的用处不在架构，在评测。今天所有 agent 报的"任务完成率"， 其完成判据来自被测系统自己。于是两件坏事同时发生：

  • 横向不可比。两个系统各自的完成标准不同，成功率不是同一个东西的两次测量。
  • 纵向可被刷。一个把"什么时候算完"放得更宽松的模型会得到更高的完成率—— 而它和真实做对程度的关系，没人量过。

我们实测到的量级就是这个风险的大小：在写类条件上，41–44% 的交付是误导性的（见第一节）。 这不是"模型不行"，这是传统 loop 里根本没有一个位置是负责在交付前把这句话和现实对一遍的。

所以这条推论的可引用形式是一句评测批评，而不是一句架构偏好：
用生成物的形状充当自己的终止条件，会让"完成率"同时失去可比性和可证伪性。

三推论二 · 判断的输入必须是证据

3.1 仪器：两个数，不是平均值

不看两组的均值差，看判定层批准的东西里有多少是误导（假警报率）、 该拦的拦住了多少（抓取率）。这类比例在事件稀少时也估得出来，而且零事件时给的是上界。

  • 每个比例都带分子和分母，不给光秃秃的百分数。
  • 区间用 Wilson；零计数用 rule of three 给上界，绝不写"0%"。
  • 弃权单独计——"我不确定"不是"我判对了"，也不是"我判错了"。
  • 配对比较用精确 McNemar；要说"没有差别"就用 TOST 等价检验 + MDE，不当"证明了零假设"。

仪器之外还有两件我们自己造的东西，是整个方法的支点： 配对操作（表面话一模一样、真值相反）和换证据（把 A 任务的证据接到 B 任务的声明上， 看判定会不会跟着动）。有了这两个，"判得准不准"才第一次有真值可对。

3.2 已经测到的三条

命题装置结果
把判定融进生成不可用 融合自评 开口时假警报 72.7–100%
真错只抓到 0/14；弃权 74–86%
解耦不够——判定器看不见证据 换证据 · judge-same 只动了 0/72、0/72、1/120 格
同一个模型、同样的问题，只是完全解耦
证据耦合有效 换证据 · 耦合判定器 抓取 40.4% vs 11.1%
匹配假警报成本；McNemar 23:6，p=0.0023

前两条合起来是"分开执行者不够"；三条合起来是一句话： 决定判定质量的是问题里带了哪些字段，不是谁来答、判几次。

四推论三 · 控制可以被单独测量和路由

对象不是"agent"，是 agent 每次跃迁时的那一个控制决策。我们已经把它拆成七个节点， 分先验（决定下一步）和后验（评价产出）两半：

C 轴是 null，这点必须先说清楚

声明式契约和等价的 if/else 我们可以证明是等价的，实验也确实测不出差别。 所以"我们提出一种新格式"不能当贡献讲。C 轴只说明一件事： 研究对象不是形式，是控制本身。

DECISION.md 的意义（重新定位）

它的意义也不是格式——是"控制可以被测量"的前提条件：把 loop 的守卫集中到一处， 可 diff、可 review、可逐点开关。守卫散在 prompt 和代码里的时候，你连"判了几次、 每次带什么字段"都数不清，更谈不上给它算抓取率。

所以要改的说法是：从"我们提出一种描述决策的格式"，改成 "我们让 agent loop 的控制第一次成为一个可测量的对象，DECISION.md 是它的载体"。

五诚实的一格：把区分做出来，不等于修好

这里有个必须自己先说的反证。我们做了一个消融：同一个循环、同一批工具、 同一个交付闸门（canDeliver 逐字复用，不是第二份实现）， 只改"判定放几次"。四条臂，ternary-judge 20 题，qwen3.5-9b 生成 + Jev 判定：

臂答对闸门假拒 闸门放过生成调用判定请求
react 没有验证者 15/200 0 构造上无闸门 690
react-termination 退出是判决点 15/200 5 6920
react-selfcheck 零资源自检 15/204 1 1370
react-typed 全程七节点 3/200 11 49273

退出变成判决点之后，那 5 条错的全放过去了。所以这条推论必须写成两层，缺一层就是过度声称：

  • 结构层（可证）：把退出变成一个判决点，是让"完成"这件事第一次可以被计数、被测量、 被路由、被逐点开关的前提。今天没有任何系统能报出自己"退出判得准不准"，因为没有那个量。 这一层的收益不依赖它准不准。
  • 效果层（已测，但看条件）：效果出在专门为假完成造出来的写类条件上（44.2% / 41.3%）， 以及匹配误伤后的 40.4% vs 11.1%（23:6，p=0.0023）；天花板 34%（18/53）。
这张表怎么读，才不会被打掉

① 取第一次裁决。修订之后再判的那个数已经被闸门影响过，拿它算"闸门错没错"是循环论证。
② react 的 0 放过不是"它从不犯错"，是构造上没有闸门，那个字段恒为假。
③ 这一格不能读成"终点验证更好"：react-typed 掉到 3/20 是任务成绩被做坏了 （本地 9B 不擅长那六种逐步判定），不是"判定放得越多越差"这条规律。
④ 放过那两栏的分母不一样（react-typed 有 17 条错的， react-termination 只有 5 条），所以 11 vs 5 不能直接比。
⑤ n=20、一个模型、一个数据集。这四条臂的用途是证明"这条臂和这两个数都活着"，不是给效应量。

六这条 claim 的界：证据的可信度

判定器的正确性上界，是它证据的可信度。

这不是一句口号，我们有它的一个具体数字。当谎言藏在证据通道里—— 工具调用静默无操作、只写了一半、或者干脆伪造输出—— 最好的 gate 也只能抓到 34%（18/53）。判定器再怎么换、怎么训、怎么解耦， 都判不出一个会撒谎的观测。

这条界把领域指向下一个方向：不是换更好的判定器，而是给观测做来源认证（provenance）。

一条能证的界比一个刷高的数有价值得多，因为它同时给出了"为什么"和"接下来该做什么"。 这也是这条 claim 最可能被 follow 的地方——它不是一个系统的介绍， 是一个可以被反驳、被复现、被继续推的命题。

八下一步（按依赖排序）

  1. 测机制：流畅度 ↔ 判定接受度的相关性。它决定我们有没有"解释"， 而不只是"测量"。最便宜，且结论会改写后面所有叙事。
  2. 补跨模型：3–4 个模型，含另一个家族，跑同一套配对操作。 这一步决定"证据盲"是现象还是某个模型的毛病。
  3. 把换证据测试搬到先验节点（pick_tool）：纯 replay，复用现成的 scripts/frame_ab.py。目的是把"先验 + 后验"合成一个控制层， 而不是两半各说各话。
  4. provenance 那一块先写成 future work，现在不做。它是天花板指出的方向， 不是我们这轮能交付的东西。
